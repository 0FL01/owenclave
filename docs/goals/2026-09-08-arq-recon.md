# ARQ reconnaissance and local recovery tests

Date: 2026-09-08
Status: assessment complete; no runtime change recommended

## Question and conclusion

Interpret ARQ as Automatic Repeat reQuest, including MasterDNS-style selective
retransmission and an extra DNS-query retry layer. No specific alternative
implementation was supplied. Determine existing reliability, exercise the pinned
library locally and distinguish evidence from a predicted LTE speedup.

Slipstream already has end-to-end QUIC stream recovery and explicitly enables
preemptive repeats. Adding another generic ARQ layer is not enabling a missing
feature. There is no measured incremental LTE benefit and no basis to deploy it.
This does not prove that every possible recovery-timer optimization is useless.

selected by `bin/lib/slipstream/build.sh` at
`bc772dd07d9a136dbd7553b0da575526de207847`. Its clean picoquic submodule is
`4bd356c004a50ec46ee8a933ebd024da5d659f75`.

- `crates/slipstream-ffi/src/runtime.rs:70-80` calls
  `picoquic_set_preemptive_repeat_policy(quic, 1)`. Both client runtime and server
  initialization use this shared setup. This is source evidence, not a new live
  server binary attestation.
- `vendor/picoquic/picoquic/loss_recovery.c` implements loss/retransmission handling;
  QUIC ACK ranges and loss/PTO recovery already provide selective recovery.
- `vendor/picoquic/picoquic/sender.c:1330-1398,3643-3673` implements conditional
  preemptive repeats, with recent-progress/receive guards and checks for eligible
  frames. Enabled does not mean that every packet is duplicated.
- `app/src/main/java/io/nekohasekai/sagernet/bg/proto/SlipstreamInstance.kt:132-163`
  already makes two attempts total per DNS query on I/O failure, reconnecting
  between attempts. TCP also retransmits segments on the client-to-resolver leg;
  it does not ensure reliability of the entire resolver-to-authority path.
- That adapter has 48 serial workers and a separate 64-query queue. Queue-full
  admission can drop a query. More repeats can occupy the same constrained workers
  and queue; they do not create capacity.
- The query age budget is not a strict whole-exchange deadline: connect and reads
  reuse a calculated timeout, and successive reads can extend elapsed time.
  This is an inspection finding, not a measured cause of current LTE slowness.
- The retained MasterDNS research checkout uses custom per-sequence ACK/NACK,
  out-of-order buffering and timed retransmission in `internal/arq/arq.go`
  (`processReceivedData`, `ReceiveAck`, `HandleDataNack`, `checkRetransmits`).
  `stream_client.go` and `stream_server.go` start ARQ for streams. It supplies
  core reliability there; transplanting it over QUIC duplicates responsibilities.

## Executed local tests

Built the unmodified pinned picoquic `picoquic_ct` target in ignored
`build/arq/picoquic`. Reused cached PicoTLS source and OpenSSL 3.5.4 static libraries
from `build/bbr3/`; used host zlib. CMake required
`PICOQUIC_FETCH_PTLS=ON`, a local `FETCHCONTENT_SOURCE_DIR_PICOTLS`, and
`CMAKE_POLICY_VERSION_MINIMUM=3.5`. Host OpenSSL initially lacked `engine.h`;
explicit cached include/library paths resolved that build failure.

From the build directory:

```sh
./picoquic_ct -S /home/stfu/.cache/owenclave-slipstream/src/vendor/picoquic \
  first_loss server_losses heavy_loss heavy_loss_inter heavy_loss_total \
  spurious_retransmit frames_repeat pacing_repeat excess_repeat \
  ec9a_preemptive_amok satellite_preemptive satellite_preemptive_fc pacing_dcubic
```

**8/13 passed; the suite is not green.** Each of the five failures was also run
alone and reproduced the same diagnostic, ruling out test-order dependence in
this run. No test expectations or library sources were edited.

The three completion-limit failures occur after scenario integrity verification
(`tls_api_one_scenario_body_verify`), not at a reported payload mismatch. The
edge-case failure is the test's nonzero-repeat assertion, not its excess-repeat
assertion. Their deeper causes remain unestablished. These are baseline findings
in the existing fork, not regressions from an ARQ candidate. Do not advertise this
run as complete recovery acceptance. Heavy-loss scenario comments and implemented
durations differ; do not interpret test names as a calibrated LTE loss profile.

Tests simulate QUIC links, not Android gVisor, the DNS TCP adapter, recursive DNS,
or the production FlowRelay/WARP path. Synthetic test artifacts stay under ignored
`build/arq/`; no production traffic logging was enabled. No LTE A/B was performed.

## Recommendation and limits

Keep the existing recovery and DCUBIC configuration. Do not add stop-and-wait,
Go-Back-N or another reliable ordered carrier around independent QUIC streams.
Selective-repeat ARQ would be sensible for a carrier without reliability, but
that is not this architecture. FEC is a different bandwidth-for-latency trade-off,
not a free ARQ switch.

A narrower investigation could examine whether stale DNS work delays QUIC
recovery, or whether the existing preemptive policy helps latency at an acceptable
query cost. Neither benefit is demonstrated here. A candidate would need paired
end-to-end goodput, loaded p95, timeout and query-overhead evidence on the same
resolver, not just successful library tests or faster synthetic completion.

No APK, native library, routing, resolver selection, server, certificate or
security setting was changed. No commit/push was requested or performed.
